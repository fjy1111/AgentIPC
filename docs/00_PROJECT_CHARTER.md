# 00 — Project Charter

## 1. 项目使命

AgentIPC 的使命是完成一个面向多智能体协作的系统层原型：在同一套 Agent 业务逻辑下，对比传统文本通信与结构化协议、非文本状态引用、跨任务共享记忆带来的通信开销、任务时延与重复计算变化。

本项目首先追求“完整闭环”，其次追求“更强创新”。

## 2. 比赛硬性目标映射

MVP 必须实现以下能力：

- 不少于 3 个 Agent；本项目固定实现 4 个。
- 覆盖规划、检索、执行、总结四类角色。
- 结构化通信，包含动作、参数、结果、能力信息。
- 支持握手、能力注册与发现。
- 同时支持 text mode 与 structured mode。
- 非文本中间状态传递。
- 共享记忆保存、检索、复用。
- 至少两组关联连续任务。
- 统计消息、文本开销、状态传递、耗时、记忆命中等指标。
- 稳定运行不少于 10 轮。
- 提交完整源码、设计文档、部署文档、实验报告和演示材料。
- 在 openEuler 24.03-LTS-SP3 上可安装、运行、测试。

## 3. 最小可提交成品定义

只有同时满足下列条件，项目才进入“可提交”状态：

1. `pip install -e .` 成功。
2. `pytest -q` 核心测试全部通过。
3. `agentipc doctor` 输出核心能力全部 ready。
4. `agentipc demo --provider mock` 成功。
5. A/B/C/D 四种实验配置均能完成。
6. 两组连续任务均能完成至少 10 轮。
7. `results/` 中能生成原始与聚合报告。
8. Dashboard 能读取已有结果并展示核心指标。
9. openEuler 验证脚本完成。
10. README、设计、部署、实验文档齐备。

## 4. 设计原则

### 4.1 Infrastructure first

Agent 的业务能力保持简单，重点是协议、状态、记忆、运行时和评测。

### 4.2 Reference instead of copy

大的中间结果与状态本体不在 Agent 消息中重复搬运，统一采用引用。

### 4.3 Mock first

核心链路不依赖网络、模型和 API Key。

### 4.4 Observable by default

所有 Agent 消息、状态传递、Memory 命中和工具调用必须可以记录和回放。

### 4.5 Fail small

任何可选模块失败时，应尽量降级而不是导致整个系统不可用。

## 5. 非目标

MVP 不追求：

- 通用 Agent 编排框架
- 多机分布式 Runtime
- 任意第三方 Agent 框架自动接管
- 复杂长期记忆理论
- hidden state 跨模型传输
- 大规模公开 benchmark 排名
- GPU 性能优化
- 复杂 Web 产品

## 6. 成功判断

项目是否成功，不以“代码量”判断，而以以下证据判断：

- 同任务 A/B/C/D 可复现
- structured 相比 text 的通信开销有可解释变化
- state 模式确实传输并消费非文本状态
- memory 模式确实复用上一任务信息并减少至少一类重复工作
- 连续任务稳定完成
- 评委能从 Dashboard 和报告快速看懂机制
